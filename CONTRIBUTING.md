# Contributing to Agent Skills Studio

Thanks for helping make these methods useful in real projects. Small fixes,
reproducible bug reports, skill improvements, translations, tests, and site
changes are welcome. You can open a PR without opening an issue first. For a
larger change or a new skill, start with an
[improvement proposal](https://github.com/jhonatan-oliveiradev/agent-skills/issues/new/choose)
so the scope and overlap with existing skills can be discussed.

For security issues, follow [SECURITY.md](SECURITY.md) instead of opening a
public issue. Be respectful and specific in discussions and reviews.

## Fork, run, and send a PR

1. Fork the repository on GitHub and clone **your fork**. Use Node.js 22 (see
   `.nvmrc`), npm, and Git. Node 20+ is supported; CI checks Node 22 on Linux
   and Windows.

   ```bash
   git clone https://github.com/YOUR_USERNAME/agent-skills.git
   cd agent-skills
   git remote add upstream https://github.com/jhonatan-oliveiradev/agent-skills.git
   npm ci --prefix apps/web
   npm test
   npm run validate
   ```

   There is no root `npm install` step: the repository root has no npm
   dependencies or lockfile. The website has its own lockfile under `apps/web`.

2. Start from the current upstream default branch and create a focused branch:

   ```bash
   git fetch upstream
   git switch main
   git merge --ff-only upstream/main
   git switch -c fix/describe-the-change
   ```

   `main` is the default and production branch. `dev` is used for integration
   of preproduction work. Open your PR against `main` unless the related issue
   or a maintainer explicitly directs the work to `dev`; if so, base your
   branch on `upstream/dev` instead.

3. Make one focused change, run the checks below, and push your branch:

   ```bash
   git push -u origin fix/describe-the-change
   ```

4. Open a pull request in the upstream repository. Fill out the PR template:
   explain the problem, what changed, how you verified it, and any tradeoffs.
   Draft PRs are welcome when you want early feedback. CI runs on PRs for
   Linux and Windows; address failures or explain environment-specific ones.

## Find the right files

| Change | Source of truth |
| --- | --- |
| Skill behavior | `skills/<slug>/SKILL.md` and any supporting files in that directory |
| Skill discovery text | `catalog/skills/<slug>.json`, with equivalent `en` and `pt-BR` locales |
| Pack membership and order | `catalog/packs/<slug>.json` |
| Catalog version and locales | `catalog/catalog.json` |
| Website and Career Lab | `apps/web/src/` |
| Installers, tooling, and validation | `install.sh`, `install.ps1`, `scripts/` |

`catalog/generated/catalog.json` is generated and committed. Never edit it by
hand; run `npm run catalog:generate` after changing source catalog JSON. Site
downloads and `apps/web/src/generated/` are generated by web scripts and are
not committed. This repository is a plain Node project with a separate Next.js
app, not an npm workspace.

For a new skill, first check existing skills for overlapping triggers. Use a
lowercase hyphenated directory name and matching `name` frontmatter. Its
`description` must begin with `Use when` and describe the situation that
triggers it. Write a reusable workflow without secrets, client data, private
URLs, or project-specific material. The
[skill authoring method](skills/turning-techniques-into-skills/SKILL.md)
shows the expected structure and pressure testing. Add bilingual metadata in
`catalog/skills/`, update affected pack metadata and membership in
`catalog/packs/`, then regenerate the catalog. If the skill belongs to no
pack, use an empty `packs` list as existing standalone skills do.

For public-facing site copy, keep `en` and `pt-BR` equivalent. For visual
changes, attach screenshots or a recording at relevant viewport sizes and
check keyboard access, reduced motion, and responsive layout where relevant.

## Run the checks

All contributions should run the root gates:

```bash
npm test
npm run validate
```

If catalog JSON changed, first regenerate it with `npm run catalog:generate`.
`npm run validate` then checks skills, metadata, generated output, and plugin.

If the website changed, run its gates too (after `npm ci --prefix apps/web`):

```bash
npm run web:test
npm run web:typecheck
npm run web:lint
NEXT_PUBLIC_SITE_URL=https://skills.jhonatanoliveira.com npm run web:build
```

To view the site locally, run `npm --prefix apps/web run dev`; visit the URL
shown by Next.js. On Windows PowerShell, set the build variable with
`$env:NEXT_PUBLIC_SITE_URL = 'https://skills.jhonatanoliveira.com'` before
`npm run web:build`. If you cannot run a gate, state which one and why in the
PR rather than claiming it passed.

# Português

Correções pequenas, relatos reproduzíveis, melhorias em skills, traduções,
testes e mudanças no site são bem-vindos. Você pode abrir um PR sem criar uma
issue antes. Para mudanças maiores ou uma nova skill, comece com uma
[proposta de melhoria](https://github.com/jhonatan-oliveiradev/agent-skills/issues/new/choose)
para discutir o escopo e a relação com as skills existentes.

Para problemas de segurança, siga o [SECURITY.md](SECURITY.md) e não abra uma
issue pública. Mantenha as conversas e revisões respeitosas e específicas.

## Do fork ao PR

1. Faça um fork no GitHub e clone **o seu fork**. Use Node.js 22 (veja
   `.nvmrc`), npm e Git. Node 20+ é aceito; o CI testa Node 22 em Linux e
   Windows.

   ```bash
   git clone https://github.com/YOUR_USERNAME/agent-skills.git
   cd agent-skills
   git remote add upstream https://github.com/jhonatan-oliveiradev/agent-skills.git
   npm ci --prefix apps/web
   npm test
   npm run validate
   ```

   Não é preciso rodar `npm install` na raiz: ela não tem dependências nem
   lockfile. O site tem seu próprio lockfile em `apps/web`.

2. Parta da branch padrão atualizada e crie uma branch para a mudança:

   ```bash
   git fetch upstream
   git switch main
   git merge --ff-only upstream/main
   git switch -c fix/descricao-da-mudanca
   ```

   `main` é a branch padrão e de produção. `dev` é usada para integrar
   mudanças antes da produção. Abra o PR contra `main`, a menos que a issue
   relacionada ou um mantenedor indique `dev`; nesse caso, crie sua branch
   a partir de `upstream/dev`.

3. Faça uma mudança focada, execute as verificações abaixo e envie a branch:

   ```bash
   git push -u origin fix/descricao-da-mudanca
   ```

4. Abra um PR no repositório original. Preencha o modelo com o problema, a
   mudança, as verificações e eventuais decisões. PRs em draft são bem-vindos
   para receber feedback. O CI roda em Linux e Windows; corrija falhas ou
   explique diferenças do ambiente.

## Onde alterar

| Mudança | Fonte de verdade |
| --- | --- |
| Comportamento da skill | `skills/<slug>/SKILL.md` e arquivos de apoio na mesma pasta |
| Texto de descoberta da skill | `catalog/skills/<slug>.json`, com idiomas `en` e `pt-BR` equivalentes |
| Membros e ordem de um pacote | `catalog/packs/<slug>.json` |
| Versão e idiomas do catálogo | `catalog/catalog.json` |
| Site e Career Lab | `apps/web/src/` |
| Instaladores, scripts e validação | `install.sh`, `install.ps1`, `scripts/` |

`catalog/generated/catalog.json` é gerado e versionado. Não o edite
manualmente: rode `npm run catalog:generate` após alterar o JSON de origem.
Downloads do site e `apps/web/src/generated/` são gerados pelos scripts web e
não são versionados. A raiz é um projeto Node comum; o app Next.js é separado.

Para uma nova skill, verifique antes se há gatilhos parecidos nas skills
existentes. Use um nome de pasta com letras minúsculas e hífens, igual ao
`name` no frontmatter. A `description` deve começar com `Use when` e indicar
quando usar a skill. Escreva um método reutilizável, sem segredos, dados de
clientes, URLs privadas ou material específico de projeto. O
[método de criação de skills](skills/turning-techniques-into-skills/SKILL.md)
mostra a estrutura e como testar casos reais. Crie metadados bilíngues em
`catalog/skills/`, atualize membros e metadados dos pacotes afetados em
`catalog/packs/` e regenere o catálogo. Skills avulsas usam `packs` vazio.

Para textos públicos do site, mantenha `en` e `pt-BR` equivalentes. Em
mudanças visuais, anexe imagens ou vídeo em tamanhos de tela relevantes e
verifique teclado, movimento reduzido e layout responsivo quando aplicável.

## Verificações

Toda contribuição deve executar os comandos da raiz:

```bash
npm test
npm run validate
```

Se alterar JSON do catálogo, rode `npm run catalog:generate` antes. O
`npm run validate` verifica skills, metadados, arquivos gerados e plugin.

Para mudanças no site, execute também (após `npm ci --prefix apps/web`):

```bash
npm run web:test
npm run web:typecheck
npm run web:lint
NEXT_PUBLIC_SITE_URL=https://skills.jhonatanoliveira.com npm run web:build
```

Para ver o site localmente, use `npm --prefix apps/web run dev` e abra o
endereço mostrado pelo Next.js. No PowerShell, defina
`$env:NEXT_PUBLIC_SITE_URL = 'https://skills.jhonatanoliveira.com'` antes de
`npm run web:build`. Se não conseguir rodar uma verificação, indique no PR
qual faltou e por quê.
