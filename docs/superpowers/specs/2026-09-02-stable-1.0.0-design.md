# Stable 1.0.0 promotion — design

## Goal

Promote Agent Skills Studio from the verified `1.0.0-rc.2` candidate to Stable `1.0.0` without changing canonical skill behavior, pack composition, or public product scope.

## Preconditions

Stable promotion is allowed only because the merged RC2 state now satisfies the explicit readiness gate:

- catalog remains 54 canonical skills / 11 active packs;
- `release/stable-readiness.json` is `ready-for-stable-review`;
- `codebase-intelligence` is present in both `requiredRealUsePacks` and `validatedRealUsePacks`;
- observed real-use evidence is 4 cases / 3 distinct projects / 5 active packs represented;
- all four public surfaces are marked Stable-ready;
- no canonical `skills/*/SKILL.md` change is required for promotion.

## Stable release contract

### Version owners

Stable `1.0.0` must be synchronized across six Studio-level release owners:

1. `VERSION`
2. root `package.json`
3. `.codex-plugin/plugin.json`
4. `catalog/catalog.json`
5. `apps/web/package.json`
6. `apps/web/package-lock.json` root package metadata

The lockfile is explicitly added to the release contract because it still reports `1.0.0-rc.1` while the package manifest is RC2. Stable must eliminate that drift.

### Catalog propagation

The existing catalog validator requires every skill and pack metadata record version to match `catalog/catalog.json.version`. Therefore promotion mechanically synchronizes:

- 54 `catalog/skills/*.json` records;
- 11 `catalog/packs/*.json` records;
- `catalog/generated/catalog.json`;
- `apps/web/src/generated/catalog.json`.

This is version propagation only. Canonical `skills/*/SKILL.md` files remain unchanged.

### Readiness record

`release/stable-readiness.json` advances to schema v4 and becomes a release-state record:

- `candidateVersion: "1.0.0"`
- `targetVersion: "1.0.0"`
- `promotedFrom: "1.0.0-rc.2"`
- `status: "stable"`

All qualifying evidence, minimums, observed totals, validated packs, and surface records remain preserved.

### Public release history

Stable adds a new `1.0.0` release entry above RC2 in:

- `CHANGELOG.md`
- localized web release history in `apps/web/src/lib/project-pages.ts`

RC2/RC1 and older release history must remain byte-for-byte semantically historical; no previous release wording is rewritten merely because Stable now exists.

## TDD contract

Before production metadata is promoted, tests must fail while requiring:

- Stable version owners at `1.0.0`, including the web lockfile;
- schema-v4 Stable readiness state;
- current Codebase Intelligence catalog metadata at `1.0.0`;
- the latest localized public release entry to be Stable `1.0.0`.

The RED must be observed in canonical GitHub Actions before the mechanical version promotion.

## Verification

The final clean PR HEAD must pass the repository's canonical `Validate skills` workflow on Ubuntu and Windows:

- root tests;
- catalog/plugin validation;
- web dependency install;
- web Vitest;
- typecheck;
- lint;
- production build;
- Bash installer smoke on Linux;
- PowerShell installer smoke on Windows.

Final review must confirm:

- 54 skills / 11 active packs unchanged;
- no `skills/*/SKILL.md` diff;
- catalog skill/pack changes are version-only;
- no temporary workflow remains;
- Stable tag/release does not exist before merge authorization.

## Merge and publication boundary

This tranche prepares the Stable release PR only. It must not merge without explicit user authorization. The `v1.0.0` git tag / GitHub Release is a post-merge publication action and is not created from the unmerged release branch.
